## 1. 一句话产品描述

**Navigator 是一个意见驱动的产品迭代系统**：把产品迭代过程中产生的所有反馈——用户的使用意见、开发者的验收意见——收进来、澄清、沉淀成目标，派发给各台机器上的 worker（agent）执行，产物合并回源码仓库，形成 **"意见 → 目标 → 执行 → 反馈"** 的闭环。它自托管在一台公网 VPS 上，用浏览器即可指挥全局。

设计动机（用户亲述的三个痛点）：

| # | 痛点 | Navigator 的回应 |
|---|---|---|
| 1 | **目标跑飞 / 没完成标准** | 目标/任务必须带完成标准；目标一旦开始不可变，只能取消；拐弯发生在目标边界 |
| 2 | **多机 / 多 agent 一片乱** | 统一能力注册 + 空闲派发 + 心跳活性 + 状态集中（Navigator 是唯一事实源） |
| 3 | **状态全靠记忆和命令** | Web 界面统一可见：任务、worker、evidence、意见、目标 |

（注意：用户明确**没有**把"定时调度/无人值守"列为痛点 → 定时调度不在产品范围内。）

## 2. 用户故事（已收录，持续补充）

> 以下故事以使用者口吻收录自共创讨论。**用户表示还有故事未讲完，本节将持续增补。**

**US-1 核心闭环（多机干活）**
我在任何一台电脑的浏览器上打开 Navigator（跑在 VPS 上），建一个任务：写明要求、完成标准、指定引擎/模型、指定目标仓库。Navigator 把任务派给一台空闲且有对应能力的 worker；worker 在自己的 git worktree 上干活，干完 commit 并 push；我在 Web 上看到 evidence，验收。

**US-2 意见收件箱**
用户会提意见，开发者自己也有意见——它们被写成一条一条的文本。Navigator 里要有一个专门收意见的地方。每条意见质量不一样：定义不清、说不明白的会被丢弃；表达清晰、明确指向改进方向的会被重视、保留。

**US-3 澄清对话**
提意见的人常常说得不明不白。可以有一个 Agent 先做初步判断，跟提意见的人简短聊几句，把一个模糊的意见聊精准——这是"抢救模糊意见"的机制。

**US-4 多渠道只是另一种聊天**
用户可能从微信、Telegram、Mattermost 来——但这些都只是入口渠道。渠道里进来的一切都被看成意见，**不会被直接执行**。第 1 期只做 Web 端聊天；Mattermost 以后接，也只是一个聊天而已。

**US-5 验收即反馈（没有重做）**
我验收一个任务，发现做得不对——我不会让它"重做"。我只会写一条验收意见："这次制作失败、败在哪"，这跟用户测出一个 bug 提一条意见是同一回事。无数条意见攒在一起，之后一起讨论出新的目标。

**US-6 目标与拐弯**
一个目标做完或取消之后，我把攒下的意见交给大脑讨论，得出下一个方向——这就是"拐弯"。**目标一旦开始执行就不变，最多取消**；不存在中途改目标。

**US-7 借脑力（远程 worker）**
有些机器有浏览器能做带 GUI 的测试，有些机器擅长别的。我希望能把任务派给"对的"那台机器，而不是我自己登录上去手动开 agent。worker 不需要暴露任何端口，它们自己连出来。

**US-8（占位）** —— 用户还有故事未讲，待补充。

## 3. 名词解释（术语表）

> 本产品一切讨论以本表定义为准。

| 词 | 定义 |
|---|---|
| **Navigator** | 中枢，跑在公网 VPS 上的常驻服务（唯一对外暴露点）。纯确定性骨架：状态机 + SQLite + WS server + 派发 + MCP server + HTTP API + Web UI。**零原生脑**（自身不含 LLM 思考），所有"想"都外包给脑会话。 |
| **Worker** | 一台参与执行的机器上的**轻量常驻进程**（不暴露任何端口，主动外连 Navigator）。职责：配对注册、心跳、接收派发、懒拉起本地 agent（ACP 模式）、双向转发 JSON-RPC、如实上报工作状态。常跑在 tmux 里当"操作台"。一台物理机可跑多个 worker。 |
| **Agent** | worker 本地具体干活的 AI CLI 实例：CC / Kimi / opencode（可能 pi）。每个 agent 可配自己的模型；按任务类型路由（写代码/写文档/画图各用各的）。 |
| **大脑（脑会话）** | Navigator 经 ACP 现请的"思考者"（用现成 harness，如 Kimi/CC），用完回收、不保留记忆。角色包括：**意见澄清员**（跟提意见的人对话）、**规划师**（把意见凝练成目标、把目标拆成任务清单、汇总意见讨论下一个方向）。Navigator 有**一个专用大脑**供自身使用（大脑会话寿命短）。 |
| **Project（项目）** | 顶层实体。绑定一个源码仓库；每个仓库是一个"空间"。意见、目标都挂在项目下。Navigator 管**多个**项目。 |
| **目标（Goal）** | 项目内的迭代单元，一个项目可有多个目标、一个一个做。目标在**独立 git worktree** 上工作。开始后不可变，只能取消。 |
| **任务（Task/Todo）** | 目标的最小工作单元，由大脑把目标拆解而成（一个目标约 8 个任务）。带要求 + 完成标准 + 引擎/模型 + 目标仓库。 |
| **完成标准** | 建任务/目标时必须写清、可验收的条件——防"跑飞"的护栏。 |
| **意见（Opinion）** | 全系统唯一输入数据。来源：渠道聊天（使用反馈）、验收反馈、开发者意见——**都是同一种数据**。模糊的丢弃、清晰的保留、可沉淀组合成目标。 |
| **验收** | 人在 Web 上对已完成任务的判定：通过，或写一条验收意见（**无重做概念**）。 |
| **Evidence** | worker 交回的"干完的证据"：commit 引用、diff 摘要、日志、截图、报告链接等。 |
| **Worktree** | git worktree。**每个目标一个独立 worktree**，目标间物理隔离。worker 在其上干活并 commit/push。 |
| **合并（Merge）** | worker push 后，把结果合回主线。合并是 Navigator 的义务（具体执行模型见 §12-①）。 |
| **拐弯** | 目标边界处的方向变更：目标完成/取消后，攒下的意见经大脑讨论得出下一个目标。 |
| **ACP** | Agent Client Protocol，驱动 agent 的协议（JSON-RPC）。语义方向：Navigator = client，agent = server。与网络拓扑无关。 |
| **MCP** | Model Context Protocol。Navigator 对外做 **MCP server**，worker 上的 agent 作为 MCP client 外连，查/写任务状态。 |
| **WS 隧道** | Navigator = WebSocket server，worker daemon = WebSocket client 主动外连建立的常驻通道。承载配对、凭证、心跳、ACP 消息转发。 |
| **配对** | worker 先连上但未授权 → 在 Navigator 侧输入配对密钥批准 → 发设备凭证 → 可吊销。配一次，重连用凭证。 |
| **能力注册** | worker 启动时**自检**并上报：能跑哪些 agent/模型、环境特性标签（浏览器/GUI/GPU/OS）、常驻项目仓库。避免声明漂移。 |

## 4. 总体架构

### 4.1 部署形态

- Navigator 跑在**一台公网 VPS** 上，是**唯一对外暴露点**；登录用**简单用户名 + 密码**。
- worker 跑在任意网络位置的机器上（家里、办公室、其他 VPS），**全部主动外连，零端口暴露**。
- 第 1 期（M0）**单机调通**：Navigator 所在机器同时兼任一个本地 worker，worker 通过真实 WS 隧道（localhost）连接——本机跑的和将来跨机跑的是**同一条代码路径**。

### 4.2 角色与职责总览

```
                   公网 VPS（唯一暴露）
┌─────────────────────────────── Navigator ───────────────────────────────┐
│  确定性骨架（纯代码，无 LLM）：                                            │
│    状态机 + SQLite（单写者） · WS server · 配对/凭证/心跳 · 派发调度        │
│    MCP server（给 agent 查/写状态） · HTTP API（给 Web） · Web UI          │
│    登录（用户名/密码）                                                     │
└───────┬──────────────────┬───────────────────┬───────────────────────────┘
        │                  │                   │
  脑会话(ACP client)   worker 隧道(WS)     MCP/HTTP(agent 外连)
        │                  │                   │
  现成 harness         worker daemon        agent（CC/Kimi/opencode/pi）
  （Kimi/CC/opencode）  └─ 懒拉起 agent ACP 模式
```

| 通道 | 方向 | 用途 |
|---|---|---|
| **WS 隧道** | worker daemon（client）→ Navigator（server）外连 | 配对/凭证/心跳；Navigator 推"开会话"；ACP JSON-RPC 双向转发 |
| **ACP** | Navigator = client → agent = server（经隧道） | 驱动 agent：发指令、会话控制（借脑力） |
| **MCP** | agent（client）→ Navigator（server）外连 | agent 干活时查/写状态：认领任务、读完成标准、交 evidence |
| **HTTP API** | Web/浏览器 → Navigator | Web UI 数据 |
| **git** | worker 本地 worktree → commit/push | 代码产物通道；合并是 Navigator 的义务 |

### 4.3 连通层（定案）

1. Navigator 起 WS server；每台 worker 的 daemon 以 WS client 外连（NAT 友好）。
2. 配对：worker 连上但未授权 → 本地（tmux）显示配对密钥 → 在 Navigator 侧输入密钥批准 → Navigator 发设备凭证 → 之后重连用凭证自动认证，凭证可吊销。
3. 心跳保活 + 断线重连（退避）；worker 如实上报状态迁移（开始 → busy，完成 → idle）。
4. 派发时 Navigator 推"开会话"消息 → worker daemon **懒启动**本地 agent（在对应 worktree/目录，ACP 模式）→ daemon 做**双向转发**：Navigator 的 JSON-RPC → agent stdio，agent 的事件/回复 → 隧道回去。每个会话对应一个 agent 实例，会话结束回收。
5. agent 要动文件/跑命令的权限请求经 ACP 回到 Navigator/用户授权。
6. worker 常跑在 **tmux** 里：密钥显示、可 attach 亲眼看 agent 干活、出问题能直接上手。

### 4.4 脑力来源（定案）

- **Navigator 零原生脑**：状态机、派发、心跳、匹配全部是确定性代码。
- **思考全外包**：所有"想"的活 = Navigator 经 ACP 开一个脑会话，请现成 harness（Kimi/CC/opencode，按任务路由模型）来当脑。
- Navigator 是**记忆**（状态全在 SQLite），脑是**每次现请的思考者**（用完回收、不保留记忆）——脑可随时换型号，状态和审计不受影响。
- Navigator 有一个**专用大脑**承担自身认知工作：意见澄清、拆解目标为任务、汇总意见讨论下一个方向。
- 微判断（如"这条意见清晰还是模糊"）首期**人工兜底**；以后可接轻量 LLM API，不启完整会话。

### 4.5 状态存储（定案）

- **SQLite，Navigator 单写者**——worker 永远不碰 DB 文件；多 worker 并发通过"只由 Navigator 写"消除。
- 状态机语义借鉴 loopx（goal/todo/gate/evidence 的思路），但**独立实现**，运行期不依赖 loopx。
- 数据只分两类通道：**轻状态**走 MCP/HTTP（Agent 或 Web 查/写）；**重内容**（代码产物）留在 git。

## 5. 意见漏斗（输入侧）

**铁律：一切输入都是意见，不被直接执行。**

```
渠道（v1：Web 聊天；以后：Mattermost/微信/Telegram = 只是另一个聊天）
   │
   ▼
意见收件箱（按项目归属）── 模糊的 ──► 丢弃
   │                    清晰的 ──► 保留入库
   ▼
澄清 agent（脑会话）：跟提意见的人简短对话，把模糊意见聊精准
   │
   ▼
沉淀：攒一段时间（天级）的零散意见 → 汇总 → 梳理 → 提炼
   │
   ▼
（到目标边界）大脑讨论：现有意见 → 得出下一个目标方向（= 拐弯）
```

- 开发者意见、用户使用反馈、**验收反馈**（US-5）都是同一种数据：意见。
- 意见入库后是后续制定目标时的**必考素材**。
- 第 1 期：意见分类靠人工兜底；只做 Web 端聊天入口。

## 6. 目标与任务

### 6.1 结构（定案）

```
Project（绑定一个源码仓库 = 一个空间）
  └── 目标 1 ── 任务清单（大脑拆解，约 8 个任务）
  └── 目标 2 ── 任务清单
  └── …（一个一个做）
```

- 每个目标在**独立 git worktree** 上工作（物理隔离）。
- **目标一旦开始执行就不变，只能取消。**
- **拐弯只发生在目标边界**：目标完成/取消后 → 攒下的意见 → 大脑讨论 → 下一个目标。

### 6.2 生命周期

```
意见库 →（大脑讨论）→ 新目标（含完成标准）→ 大脑拆解成任务清单
   → 逐任务派发执行 → 全部完成 → 你验收/复盘 → 目标收尾
   →（此时看意见库）→ 大脑讨论下一方向（拐弯）
        ↑                                        │
        └──────────── 新意见不断进来 ←────────────┘
```

## 7. 执行与验收

### 7.1 任务结构（草案字段）

```yaml
task:
  id:
  goal_id:            # 所属目标
  project_id:         # 所属项目（决定仓库空间）
  worktree:           # 目标的独立 worktree
  title:              # 人话
  requirement:        # 要求
  acceptance:         # 完成标准（可验收）
  engine:             # cc | kimi | opencode | pi
  model:              # 可选，按任务类型路由
  worker_id:          # 派给谁（空闲 + 有能力）
  state:              # queued | running | done | cancelled
```

### 7.2 派发模型（定案）

```
Navigator 派发（无婉拒、无竞标）：
  1. 能力注册表筛选候选（能跑这任务、有这仓库/引擎/模型的 worker）
  2. 从候选中挑"空闲"的（Navigator 维护在线/忙碌/离线状态）
  3. 直接派发 = 命令，不是商量
  worker 接受 = 开始干活（状态 → busy）→ 干完 → idle
```

- 能力注册：启动自检上报（引擎/模型、环境特性标签、常驻仓库），避免声明漂移。
- 空闲状态的真伪靠 worker **如实上报状态迁移**；worker 中途死掉靠**心跳丢失**兜底 → 任务标记失败/重新入队。
- 未来可选（不改协议）：若把"自己也日常在用的电脑"注册成 worker，daemon 检测到人在用时把自己标记为不可用——只是一个更丰富的状态。

### 7.3 产物回传与合并（定案 + 一个待定）

- worker 干完必须在自己的 worktree 上 **commit + push**。
- worker 上报"干完"时，**合并是 Navigator 的义务**——由 Navigator 合并，或指派一个 worker 做合并。
- **待定**：合并由谁执行、冲突怎么处理（见 §12-①）。

### 7.4 完成判定（定案）

- v1 **人验为主**：任务完成 → Web 上看 evidence → 判定"通过"或写一条**验收意见**。
- **没有重做概念**：验收不过 = 生成一条意见入库，与测出 bug 同构；无数意见汇总后一起讨论成下一个目标。

## 8. Navigator 职责清单

| 域 | 职责 |
|---|---|
| **A. 收意见** | 渠道接入（v1 Web 聊天）；一切输入=意见不直接执行；澄清 agent 对话；分诊（模糊丢/清晰留）；意见按项目沉淀 |
| **B. 定航线** | 汇总意见 → 经大脑讨论凝练目标；目标带完成标准；拐弯发生在目标边界 |
| **C. 派发驾驶** | 经 WS 隧道推"开会话"→ worker 懒拉起 agent（ACP 模式）→ Navigator 作为 ACP client 驱动（借脑力）；权限请求回到用户授权 |
| **D. 状态中枢** | 状态机 + SQLite（单写者，worker 不碰 DB）；对外 MCP server（agent 查/写状态）；对外 HTTP API；Web UI（建任务/看状态/验收/看 evidence） |
| **E. 管 worker** | WS server + 配对授权（密钥批准→设备凭证→可吊销）+ 心跳保活 + 在线/忙闲可见；能力注册表；按能力/空闲派发；合并义务（模型待定） |
| **F. 记忆与脑** | Navigator=记忆（SQLite），脑=现请的思考者（专用大脑：澄清/拆解/讨论方向），脑经 MCP 访问状态、用完回收 |

## 9. 数据模型（草案）

```
Project 1───* Goal 1───* Task 1───* Evidence
  │            │            │
  │            ├── worktree（git worktree，目标独立）
  │            └── state: active | done | cancelled（不可变，只可取消）
  │
  ├───* Opinion（意见：source=chat|acceptance|developer
  │        state=待澄清|已澄清|已采纳|已丢弃；挂在项目下）
  │
  └───* Worker 1───* Agent（engine/model/能力标签/状态）
             │
             ├── 当前任务（busy 时）
             └── 配对凭证 / 心跳时间

Task: requirement / acceptance / engine / model / worker / state
     （验收意见 = 指向 Task 的 Opinion）
```

## 10. 里程碑

### M0 · 单机闭环（先做这个）

**目标**：一台机器上同时跑 Navigator + 一个本地 worker（worker 走真实 WS 隧道连 localhost），跑通完整执行闭环。

- [ ] Navigator 骨架：SQLite 状态库 + HTTP API + 极简 Web（登录：用户名/密码）
- [ ] WS 隧道 + 配对（密钥批准→设备凭证）+ 心跳
- [ ] worker daemon（本机）：外连、收"开会话"、懒拉起本地 agent（ACP 模式）、双向转发
- [ ] 建任务（要求 + 完成标准 + 引擎/模型）→ 派发（空闲即派）→ agent 在 worktree 干活 → commit/push
- [ ] 合并（按 §12-① 定的模型）
- [ ] Web 验收：看 evidence → 通过 / 写验收意见
- **验收**：手动跑通一次"建任务 → 派发 → 执行 → 回传 → 验收"闭环；本机跑的与将来远程是同一代码路径。
