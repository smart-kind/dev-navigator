## 1. 一句话产品描述

**Navigator 是一个 Spark 驱动的产品迭代系统**：把产品迭代过程中产生的一切模糊想法——使用反馈、验收意见、开发者新点子、用户故事——忠实收进 **Spark 板**，攒到一定程度后由人发起、经**大脑语义讨论**凝练成目标，派发给空闲且有能力的 worker（agent）执行，产物经目标验收后合并回源码仓库，形成 **"Spark → 目标 → 执行 → 反馈（新 Spark）"** 的闭环。自托管在一台公网 VPS 上，浏览器即指挥台。

设计动机（用户亲述的三个痛点）：

| # | 痛点 | Navigator 的回应 |
|---|---|---|
| 1 | **目标跑飞 / 没完成标准** | 目标必须带完成标准；目标一旦开始不可变、只能取消；拐弯只发生在目标边界 |
| 2 | **多机 / 多 agent 一片乱** | 能力注册 + 只派空闲 + 心跳活性 + 状态集中（Navigator 唯一事实源），worker 零暴露 |
| 3 | **状态全靠记忆和命令** | Web 统一可见：项目/目标/任务/机器/Spark 板/架构 |

核心循环：

```
用户、我、AI 的一切想法 ──► Spark 板（忠实记录，丢弃=状态不删除）
        ▲                              │ 攒一堆后，人发起
        │                              ▼
  验收/新反馈/使用意见 ◄── 大脑语义讨论 ──► 目标（独立 worktree，不可变）
（又是 Spark）             人拍板          │ 大脑拆解
                                          ▼
                              任务 → 派给空闲 worker → 执行 → 自验
                                          │
        合并到主分支（目标验收通过后）◄──────┘
```

## 3. 名词解释（术语表）

> 术语表定义"词"。**注意：专有名词 ≠ 系统实体**——哪些词是实体（有身份/状态/生命周期）、实体间关系如何，见 §4。

| 词 | 定义 |
|---|---|
| **Navigator** | 中枢，跑在公网 VPS 上的常驻服务（唯一对外暴露点）。纯确定性骨架：状态机 + SQLite + WS server + 派发 + MCP server + HTTP API + Web UI。**零原生脑**，所有"想"外包给脑会话。 |
| **Worker** | 一台机器上的**轻量常驻进程**（不暴露端口，主动外连 Navigator）。配对注册、心跳、收派发、懒拉起本地 agent（ACP 模式）、双向转发、如实上报状态。常跑在 tmux 里当操作台。一台物理机可跑多个 worker。 |
| **Agent** | worker 本地干活的 AI CLI 实例：CC / Kimi / opencode（可能 pi）。各自可配模型；按任务类型路由。 |
| **大脑（脑会话）** | Navigator 经 ACP 现请的"思考者"（现成 harness：Kimi/CC/opencode），用完回收、不保留记忆。角色：**澄清员**、**规划师**（含语义校验）、**讨论者**。Navigator 有**一个专用大脑**承担自身认知工作。 |
| **Project（项目）** | 顶层空间。绑定**一个或多个源码仓库**（无一一对应限制）。Spark、目标都在项目空间内。Navigator 管多个项目。 |
| **Repo（仓库）** | 项目绑定的 git 源码仓库（可多个：前端/后端…）。有自己的主分支。 |
| **Spark（零星想法卡）** | 系统**唯一输入数据**：一条使用反馈 / 验收意见 / 作者新想法 / 用户故事。忠实记录，丢弃是状态不是删除。 |
| **Spark 板** | 每个项目一块，收集该项目的所有 Spark 卡。 |
| **丢弃（状态）** | Spark 的一种状态＝"不予考虑"：胡扯 / 与另一条重复 / 不可行。**不是删除**，数据永远保留可回看；重复的卡指向被采纳的那条。 |
| **已考量（状态）** | Spark 被某目标引用覆盖后置此状态＝失效，不再参与后续提案讨论。 |
| **开放标签** | Spark 卡在添加时由大脑打上的自由标签（不设固定分类），供将来筛选。 |
| **Channel（渠道）** | 对话从哪进来：Web 聊天页、以后的 Mattermost……Navigator 的界面本身就是一种输入方式。 |
| **Conversation（对话）** | 一次与大脑的聊天（人可参与），渠道无关；是 Spark 卡最常见的落地现场。 |
| **Goal（目标）** | 项目内的迭代单元。独立 worktree；**开始后不可变，只能取消**。带完成标准。 |
| **Worktree** | git worktree。每个目标一个独立工位，目标间物理隔离。 |
| **Task（任务）** | 目标的最小工作单元，由专用大脑拆解（一个目标约 8 个任务）。带要求/验收词/引擎/模型。 |
| **完成标准** | 目标/任务必须写清、可验收的条件——防"跑飞"的护栏。 |
| **验收** | 两个层次：任务级＝agent **自验**（内部修到过为止）；目标级＝人对照目标完成标准判定，**通过后才合并主分支**。 |
| **Evidence** | 干完的证据：commit 引用、改动摘要、日志、截图、报告。 |
| **合并（Merge）** | 目标验收通过后，把目标成果并入仓库主分支的动作（执行者待定，见 §14-①）。 |
| **拐弯** | **目标之间的大方向选择**（如"本来没想发明船，做到中期想发明船"）。目标内部永不拐弯。由人发起。 |
| **语义校验** | 定目标时，大脑读架构记录（实体/职责/关系），从语义上判断目标是否违背某节点职责、是否需要新增节点/改职责——作为讨论依据给人拍板。非规则硬拦，也非仅参考。 |
| **ACP** | Agent Client Protocol（JSON-RPC）。语义方向：Navigator=client、agent=server。与网络拓扑无关。 |
| **MCP** | Model Context Protocol。Navigator 对外做 MCP server，agent 作为 client 外连查/写状态。 |
| **WS 隧道** | Navigator=WS server，worker daemon=WS client 外连的常驻通道：承载配对/凭证/心跳/ACP 转发。 |
| **配对** | worker 先连上未授权 → Navigator 侧输密钥批准 → 发设备凭证 → 可吊销。配一次，重连用凭证。 |
| **能力注册** | worker 启动自检后上报：引擎/模型、环境标签（浏览器/GUI/GPU/OS）、常驻仓库。 |
| **ArchView（架构视图）** | 一张架构图＝一个视图，描述任意范围（整项目/单仓库/子系统/跨切面），不强制对应层级；同一项目可有多张并存。 |

## 4. 实体与关系（系统架构视图）

> 本节是本文档的核心新增：**术语表管"词"，本节管"系统里到底有哪些实体、它们之间什么关系、各自职责是什么"**。这些内容在系统里不是文档，而是**数据库记录**（§4.4）。

### 4.1 实体清单

| 实体 | 一句话定义 | 关键状态/属性 |
|---|---|---|
| **Person（账号）** | 能登录 Navigator 的人 | 用户名/密码 |
| **Channel（渠道）** | 输入/对话入口（Web 聊天页、以后 Mattermost…） | 类型 |
| **Conversation（对话）** | 一次与大脑的聊天，渠道无关，人和 Agent 都能参与 | 归属项目、参与方 |
| **BrainSession（大脑会话）** | 大脑的一次具体会话（角色：澄清/规划/讨论/语义校验） | 角色、引擎、模型 |
| **Project（项目）** | 顶层空间 | 名称 |
| **Repo（仓库）** | 项目绑定的源码仓库（**一项目可多个**） | git 地址、主分支 |
| **SparkBoard（Spark 板）** | 每项目一块，收本项目所有 Spark | 归属项目 |
| **Spark** | 一条零星想法/反馈/故事 | 状态（open/已考量/丢弃）、开放标签、来源、引用它的目标 |
| **Goal（目标）** | 项目内迭代单元，独立 worktree | 完成标准、状态（active/done/cancelled）、引用 Sparks |
| **Worktree** | 目标的独立 git 工位 | 分支、所属 Goal |
| **Task（任务）** | 目标拆出的最小工作单元 | requirement/验收词/engine/state |
| **Worker** | 机器上的常驻执行进程（只外连） | 配对凭证、心跳、状态（online/busy/idle） |
| **Agent** | worker 本地干活的 AI CLI 实例 | 引擎、模型 |
| **Capability（能力报告）** | worker 启动自检上报的本事清单 | 引擎/模型、环境标签、常驻仓库 |
| **ACPSession（执行会话）** | 派发后在 worker 上临时建立、Navigator 驱动 agent 的会话 | 对应 Task/Agent，随任务结束回收 |
| **Evidence** | 干完的证据 | commit 引用、日志、截图 |
| **ArchView / ArchNode / ArchRelation / ArchTerm** | 架构图视图 / 实体记录 / 关系记录 / 名词记录 | 见 §4.4 |

### 4.2 实体关系总图

```
 Person（账号）──登录──► Navigator
   │
   ▼ 经某 Channel（Web 聊天 / 以后 Mattermost…）
 Conversation ──► BrainSession（澄清/规划/语义校验，ACP 驱动现成 harness）
   │                        │
   │ 聊天现场                │ 分析、拆解、语义校验
   ▼                        ▼
 Project 1───* Repo（多仓库）── 每项目一块 ──► SparkBoard ──* Spark
   │                                            ▲
   │ 定目标时引用，被考量的 Spark→已考量(失效)    │ 人/AI/验收都能落卡
   ▼                                            │
 Goal（1──1 Worktree，不可变/只可取消）──────────┘
   │ 专用大脑拆解
   ▼
 Task ──派发(能力+空闲，无婉拒/竞标)──► Worker ──1──* Agent（经 WS/ACP）
   │                                          │ 在 Goal 的 Worktree 上干活→commit/push
   │◄──────── Evidence ───────────────────────┘
   ▼
 Goal 全部任务完成 → 目标级验收（人）→ 通过 → 合并到 Repo 主分支
   ▼
 验收不过 / 新想法 / 使用反馈 ──► 又落一张 Spark 卡（回到 SparkBoard，循环成立）
```

### 4.3 名词、实体、视图三者的关系

- **名词（Term）**：对"词"的解释，可能指协议/机制/动作（如 ACP、合并），不一定是实体。
- **实体（Node）**：有身份、有状态、有生命周期的对象（上表 17 个）。
- **关系（Relation）**：实体之间的边（属于、引用、派发、驱动、合并…）。
- **视图（ArchView）**：把若干实体+关系组织成**一张图**，描述某个范围。**同一项目可按不同维度有多张架构图**（前端一张、后端一张、跨仓库一张），不存在"一个项目对应一张图"或"全局一张图"的强制对应。实体可被多张图引用。

### 4.4 架构数据与语义校验

- **实体、关系、职责、名词全部是数据库记录**，不是静态文档。
- Navigator 自己的架构也按同一套机制被记录和维护（dogfood：Navigator 作为一个项目被自己迭代）。
- **语义校验**：人发起定目标时，大脑读取相关 ArchView 记录，从语义上判断：目标会动到哪些节点？是否违背某节点的职责？是否需要新增节点或修改职责？——把判断连同理由放进提案供人讨论。**不是规则硬拦**（职责是散文，规则引擎拦不了），**也不是只列参考**（是真正基于理解的校验）；决定权在人。
- Dashboard 设"架构"页：可视化各 ArchView、点开节点看职责、可编辑维护（人手 + 大脑辅助）。排期 M1+。

## 5. 总体架构

### 5.1 部署形态

- Navigator 跑在**一台公网 VPS**，是**唯一对外暴露点**；登录：**简单用户名 + 密码**。
- worker 跑在任意网络位置的机器上，**全部主动外连，零端口暴露**。
- **M0 单机调通**：Navigator 所在机器兼任一个本地 worker，走真实 WS 隧道（localhost）——本机与将来远程是**同一条代码路径**。

### 5.2 角色与通道

| 通道 | 方向 | 用途 |
|---|---|---|
| **WS 隧道** | worker daemon（client）→ Navigator（server）外连 | 配对/凭证/心跳；推"开会话"；ACP 双向转发 |
| **ACP** | Navigator=client → agent=server（经隧道） | 驱动 agent 干活、驱动大脑思考 |
| **MCP** | agent（client）→ Navigator（server）外连 | agent 干活时查/写状态（认领/读完成标准/交 evidence） |
| **HTTP API** | Web → Navigator | Web UI 数据 |
| **git** | worker 在 Goal 的 Worktree 上 commit/push | 代码产物通道；目标验收后合并主分支 |

### 5.3 连通层

1. Navigator 起 WS server；worker daemon 以 WS client 外连。
2. 配对：连上未授权 → worker 本地（tmux）显示密钥 → Navigator 侧输密钥批准 → 发设备凭证 → 重连自动认证，凭证可吊销。
3. 心跳保活 + 断线重连（退避）；worker 如实上报状态迁移（开始→busy、完成→idle）。
4. 派发 = Navigator 推"开会话" → daemon **懒启动**本地 agent（对应 worktree，ACP 模式）→ 双向转发 JSON-RPC；每会话对应一个 agent 实例，会话结束回收。
5. agent 要动文件/跑命令的权限请求经 ACP 回到用户授权。
6. worker 跑在 **tmux** 里：密钥显示、可 attach 亲眼看、出问题直接上手。

### 5.4 脑力来源

- **Navigator 零原生脑**；**思考全外包**：经 ACP 开会话请现成 harness（按角色/任务路由模型）。
- Navigator 是**记忆**（SQLite），脑是**现请的思考者**（用完回收、不保留记忆）——脑可换型号，状态与审计不受影响。
- **专用大脑**承担 Navigator 自身认知工作：澄清、拆解目标、讨论方向、语义校验。
- 微判断（如 Spark 打标签的初筛）可人工兜底，以后可选轻量 LLM API。

### 5.5 状态存储

- **SQLite，Navigator 单写者**——worker 永不碰 DB；多 worker 并发靠"只由 Navigator 写"消除。
- 状态机语义借鉴 loopx（goal/todo/gate/evidence 思路），**独立实现**，运行期零依赖。
- 轻状态走 MCP/HTTP；重内容（代码产物）留在 git。

## 6. Spark 板（输入侧）

**铁律：一切输入都是 Spark，不被直接执行。**

- **忠实记录**：人对项目输入的一大堆文字，**不管合不合理、有没有序，全都忠实记录下来**，一条落一张卡。
- **落卡来源**：人添加；Agent 添加；任务/目标的验收不过由系统自动落卡；用户讲的一个故事也可以是一张卡。
- **澄清**：模糊的卡可以跟大脑（澄清员）聊几句聊精准——抢救模糊想法；原文永不丢，聊天现场保留在 Conversation。
- **标签**：卡添加时由**大脑打开放标签**（不设固定分类），供筛选。
- **状态**（不是删除）：`open`（新收待处理）→ `已考量`（被某目标引用覆盖＝失效，不再参与提案）；或 → `丢弃`（不予考虑：胡扯 / 重复 / 不可行；**不删除**，重复的卡指向被采纳的那条，随时可回看）。
- **触发**：**没有人会提醒你处理 Spark**——攒一堆（如 80 条）后由**人主动**发起定目标，从中抽取（如 10 条）形成目标，并标定这 10 条"已在目标 X 中被考量"→ 失效。不会为一条 Spark 建目标。
- **归属**：Spark 挂在项目下（每项目一块板）。

## 7. 目标与任务

### 7.1 结构

```
Project（绑定一个或多个源码仓库）
  └── 目标 1 ── 任务清单（专用大脑拆解，约 8 个任务）── 独立 worktree
  └── 目标 2 ── 任务清单
  └── …（一个一个做；目标是当时人+机器共同想法的产物）
```

### 7.2 规则（定案）

- 每个目标在**独立 git worktree** 上工作（多仓库项目的 worktree 切分见 §14）。
- **目标一旦开始执行就不变，只能取消。** 想改别的 = 下一个目标的事。
- **没有"目标方向错了"这回事**：目标在制定时刻就是对的，去执行；若事后发现没意义，**人把整个 worktree 抛弃**，重新开新目标继续迭代——不在错误基础上拐弯。
- **拐弯 = 目标之间的大方向选择**，由人发起（参考 Spark 板 + 架构语义校验），目标内部永不拐弯。
- 制定目标流程：人发起 → 引用 Spark 池（被覆盖的标"已考量"失效）→ 大脑语义校验（对照架构记录：动到谁/是否越职责/要不要新节点）→ 人拍板 → 大脑拆任务清单 → 人过目 → 开工。

### 7.3 任务拆解与可行性

- 专用大脑把目标拆成 to-do 清单，每条 to-do = 一个任务，派给一个 Agent。
- **拆解时即判断可行性**——不会拆出"摘月亮"这种不可行任务；因此**不存在严格意义的"任务失败"**，只有执行得好坏（见 §8）。

## 8. 执行与验收（分层模型）

> 本版核心修正：验收/合并按主体分层，不存在笼统的"谁先谁后"。

### 8.1 任务级（Agent 自验，不合并）

- 任务派给 Agent 后，Agent 在自己的 worktree 上执行。
- Agent 内部验证不通过（如"按钮点了没反应"）→ **它自己修复重做，直到自己验收通过**——这是 Agent 内部循环，不算失败、不算重做概念。
- 任务完成后：**不发生合并**——阶段性成果留在分支上，作为该目标房间的一部分。
- 任务可上报 evidence（commit 引用/改动摘要/日志/截图）供可见。

### 8.2 目标级（人验收，通过才合并）

- 目标所有任务完成 → Navigator 看到该 worktree（"房间"）里所有任务的成果齐了——**此时仍不涉及与主项目的合并**。
- 先做**目标级验收**：人对照目标完成标准判定整体是否达成。
  - **通过** → 合并到项目主分支 → 目标 done。
  - **不通过** → 系统落一张验收 Spark（"这次制作失败、败在哪"），与用户测出 bug 同构；目标可取消/搁置，验收 Spark 汇入 Spark 板，供下一轮目标讨论。**没有返工**：补正 = 未来的新目标。
- Evidence 在任务级即可见；合并只在目标验收通过后发生一次。

### 8.3 执行参数（不是设计，是可调参数）

- 会话时长上限、重试次数（默认重试 2，可改 3…）、心跳超时等一律为**配置参数**，不在故事/架构层讨论。
- worker 中途掉线 = **执行会话中断**：任务回队列可重新派发（也算不上"失败"）。

## 10. Navigator 职责清单

| 域 | 职责 |
|---|---|
| **A. 收 Spark** | 渠道接入（v1 Web 聊天）；一切输入=Spark 不直接执行；澄清对话；忠实记录 + 大脑打开放标签 |

| **G. 架构规格** | 维护实体/关系/职责/名词记录与 ArchView；为目标讨论提供语义校验依据（M1+） |

## 11. 里程碑

### M0 · 单机闭环（先做）

一台机器：Navigator + 一个本地 worker（真实 WS 隧道连 localhost），跑通完整执行闭环。

- [ ] Navigator 骨架：SQLite 状态库 + HTTP API + 极简 Web（用户名/密码登录）
- [ ] WS 隧道 + 配对（密钥批准→设备凭证）+ 心跳
- [ ] worker daemon（本机）：外连、收"开会话"、懒拉起 agent（ACP 模式）、双向转发
- [ ] 项目（绑定仓库）→ 目标（完成标准）→ 大脑拆任务（或手动建单任务兜底）→ 派发（空闲即派）
- [ ] agent 在 worktree 干活 → 自验 → commit/push → evidence
- [ ] **目标级验收 → 通过后合并主分支**（按 §14-① 定的执行模型）
- **验收**：手动跑通"建项目→定目标→拆任务→派发→执行→自验→验收→合并→看 evidence"一次；本机与将来远程同一条代码路径。

### M1+（草稿建议，待用户故事补齐后重排）

- Spark 板 + Web 聊天 + 澄清（§6）
- 定目标流程：引用 Spark + 大脑语义校验 + 拆解（§7.2）
- 架构页与架构数据维护（§4.4、§9）
- 多 worker / 远程机器接入
- Mattermost 渠道（= 另一个聊天）
- 合并执行模型定型、evidence 大件引用方案

## 12. 明确不做（首期范围外）

- 远程多机（M0 单机，但代码路径与远程一致）
- 实时 ACP 驾驶 / 中途纠偏 / 中途改目标
- L0–L3 介入等级、Surrogate、checkpoint 停人、Takeover
- 定时调度 / 无人值守（用户未选为痛点）
- 部署环节（v1 不部署）
- Mattermost / 微信 / Telegram 接入（v1 只做 Web 聊天）
- "任务重做"概念（Agent 内部自修除外；补正=新目标）
- 目标中途变更（只可取消 / 弃 worktree）
- 架构"规则硬校验"（一律走语义校验，人拍板）
- 无人值守的任何自动触发（一切由人发起）

## 13. 状态与关键字段（摘要）

**Spark**：`id / project_id / 原文 / 来源(human|agent|acceptance|story|channel) / 状态(open|considered|discarded) / 丢弃原因(胡扯|重复→指向卡|不可行) / 标签[] / 引用目标(considered 时) / conversation_id / 时间`

**Goal**：`id / project_id / title / completion(完成标准) / 引用 sparks[] / state(active|done|cancelled) / worktree(s)`

**Task**：`id / goal_id / title / requirement / 自验标准 / engine / model / worker_id / state(queued|running|done|interrupted) / evidence[]`

**Worker**：`id / host / 配对凭证 / 心跳 / state(online|busy|idle) / capabilities[]`

**ArchNode**：`name / 定义 / 职责[] / 状态` · **ArchRelation**：`from / to / 类型 / 说明` · **ArchView**：`名称 / 范围描述 / 节点与边引用[] / 术语[]`

## 14. 待决策问题

1. **合并执行者**：目标验收通过后，合并谁来做？a) Navigator 本体确定性合并（无冲突时）；b) 大脑派合并任务给 worker（有冲突要判断时）；c) 专职合并 worker。取决于专用大脑是否具备合并能力——有就派给它。
2. **专用大脑选型**：用哪个 harness/模型做规划脑/澄清员/语义校验；大脑会话调度方式。
3. **用户故事未讲完**：US 待补充，影响 M1+ 排序。
4. **loopx 参考**：设计阶段需克隆 loopx（仓库地址/本机路径待提供），Web 可见性参考其 dashboard/registry。
5. **产品正式命名**：Navigator 暂定。
6. **多仓库项目的 worktree 切分**：一个目标跨前端+后端两个仓库时如何映射（每仓库一个 worktree？）。

8. **澄清落地细节**：澄清后是否生成精炼卡并链回原文（忠实记录前提下）；标签由大脑打的时机。
