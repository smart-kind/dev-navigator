# Spark 板 · 详细设计

> 版本目录：v0.1.2 · 配套 `../prd.md` §6 · 日期：2026-09-09
> 本文档是"输入侧"的字段级/流程级设计：Spark 何时建、描述什么、生命周期、板的功能与条目表现、汇总分类。

---

## 1. 设计原则

1. **零摩擦**：收想法比整理想法重要一百倍。建卡不带任何强制动作。
2. **忠实记录**：原文永不丢、永不删。丢弃/已考量只是状态。
3. **加工可重算**：标签、分类是**派生数据**，随时可由大脑重算，不是卡的固有属性。
4. **批量处理**：几百条 Spark 的处理是"批"不是"逐条"；单条只有收和状态流转。
5. **人发起**：没有任何自动触发；汇总分类、提炼故事卡都由人点。

---

## 2. Spark 是什么时候建立的（创建时机）

任何"一句还没想好的话"都可以立即成为一张 Spark：

| 来源 | 触发 | 落卡内容 |
|---|---|---|
| 聊天即落 | 在 Web 聊天（以后 Mattermost 等渠道）里说话 | 原话（含"我觉得不太对"这种模糊话） |
| 手动添加 | Spark 板页"添加一张卡" | 粘贴/输入的一段话、一条用户故事 |
| 验收自动落卡 | 目标级验收不通过 | 人写的验收意见（"败在哪"），来源=acceptance |
| Agent 落卡 | agent 执行中发现值得记的事（可选） | 其陈述 |
| 导入 | 把整段文字（如本文档）贴进来 | 一段文本，可拆多条或一条 |

规则：
- **创建即成功**：不校验"够不够清晰、有没有价值"——那正是后续加工的事。
- 每条卡保留**原文**字段；后续任何澄清/改写都**另存**，不改原文。

## 3. Spark 描述什么（内容结构）

```yaml
spark:
  id:                    # 稳定 id
  project_id:            # 属于哪个项目（必填——在哪块板）
  text:                  # 原文（核心，忠实，永不改）
  source:                # human | agent | acceptance | story | channel
  created_at:
  # —— 以下都是可空/派生/加工物 ——
  starred: false         # 用户手动星标（意图，AI 不代劳）
  status: new            # 见 §4
  discard_reason:        # status=discarded 时：胡扯 | 重复(→代表卡id) | 不可行
  considered_by:         # status=considered 时：被哪个 goal 引用
  cluster_ids: []        # 派生：进过哪些簇
  conversation_id:       # 澄清/产生它的聊天现场（可空）
  notes: []              # 加工记录：澄清改写、大脑标注等（只增不改）
```

**刻意不做**：不做结构化模板（谁/什么/为什么 那是故事卡的事）；不做建卡强制标签；不做优先级排序字段（那是簇/故事卡阶段的事）。

## 4. 生命周期（状态机）

```
                （人手动 / 聊天 / 验收自动）
                        │
                        ▼
                    ┌─ new（新收，待处理）─────────────┐
                    │                                  │
                    │ 人发起"汇总分类"                  │ 人点"丢弃"
                    ▼                                  ▼
              ┌─ clustered（已归簇）            discarded（丢弃）
              │   派生：cluster_ids 非空            · 胡扯 / 重复 / 不可行
              │                                  · 不删除，可回看
              ▼ 人拍板把它所在簇提炼成目标时         · 重复卡 → 指向代表卡
         considered（已考量 = 失效）
              · considered_by = goal_id
              · 不再参与后续汇总分类/提案
```

- 状态转换**只增不覆盖**：每次变化留痕（notes 或独立历史表），满足审计。
- `discarded` 和 `considered` 都是终态（卡不再流动）；唯一例外：人手动撤销（如"其实那条还能用"）→ 回到 new。

## 5. 标签策略（回应"建卡要不要打标签"）

**结论：建卡零标签；检索与分类全部派生。** 理由：

1. 分类可重算——AI 随时能对全量重分类，标签不必在创建时固化；
2. 创建时任何额外动作都在伤害"随手记"；
3. 语义搜索（自然语言）已能覆盖"找跟设置有关的"这类需求。

系统内两种"标记"分清楚：

| 标记 | 谁打 | 性质 |
|---|---|---|
| **星标 starred** | 用户手动 | 意图（"这条我特别在意"），AI 不代劳 |
| **簇 cluster_ids** | 大脑（汇总分类时） | 派生，可重算，不作卡固有属性 |

## 6. 汇总分类（批量加工，核心功能）

触发：人发起（圈定项目 / 时间段 / 全部）。

流程：
1. 人选择范围 + 提示语（可选："按痛点分"或"自由分"）；
2. 大脑读范围内所有 `new` + `clustered` 卡（`considered/discarded` 默认排除，可显式包含）；
3. 产出若干**簇**：

```yaml
cluster:
  title: "设置太难找"
  summary: "7 条在说同一件事：设置层级太深"
  member_sparks: [id…]
  representative: id   # 重复合并：代表卡
  duplicates: {id: id} # 重复卡 → 指向代表卡（重复卡标 discarded(重复)）
  suggested_story:     # 可选：大脑顺手草拟的故事卡（见 §7 与 goal-story-card spec）
```

4. 结果落库为视图/候选；大脑可解释"为什么这么分、哪些卡没进任何簇（散卡）"。

规则：
- 簇是**派生视图**：重跑会重新生成（可保留历史版本供对比）；
- 同义多条（你/我/他都说同一件事）→ 取一代表卡，其余标 `discarded(重复→代表卡)`——**不删除**；
- 散卡（没聚成气候的）留在 new，不强行归类。

## 7. Spark → 故事卡（目标）的通道

一条 Spark 不产生目标；**一个簇（或簇的组合）才可能产生一张故事卡**：

1. 人从汇总分类结果里挑一个簇（或跨簇挑几张卡）；
2. 让大脑把它们**提炼成一张故事卡**（要素见 `goal-story-card-design.md`：谁/要什么/为什么/验收标准/边界）；
3. 人过目修改 → **拍板** → 故事卡变 Goal；
4. 该簇涉及的所有 `new/clustered` 卡 → `considered(considered_by=该goal)`，不再参与后续提案；
5. 草稿故事卡（suggested_story）只是提案，拍板前不改任何卡状态。

## 8. Spark 板：界面功能清单

**收**
- 添加卡（textarea，零表单）；聊天入口（说话即落卡）；验收自动落卡入口（无界面动作）。

**看**
- 卡片流：原文大字优先；小字元数据（来源/时间/状态/簇/被引用目标/星标）；
- 展开卡：澄清聊天记录（conversation）、加工 notes、丢弃原因、重复指向；
- 筛选：状态 / 来源 / 时间 / 是否星标；**语义搜索**（自然语言）；
- 视图切换：全部 / 只看簇 / 只看散卡。

**批**
- 发起汇总分类（选范围 → 看簇 → 调整）；标丢弃（单条/批量，选原因）；星标/取消星标。

**审计**
- 任何卡不删除；状态与去向（被哪个目标考量）全可见；历史留痕。

## 9. 数量级与性能（设计假设）

- 单项目几百到几千张卡是常态；SQLite 全文/语义搜索够用；
- 汇总分类是重活（大脑要读全量卡）→ 建议按簇缓存 + 增量重跑，v1 可先全量重跑（量小）。

## 10. 开放问题（进主干 §14 待决策）

- O1：澄清对话产物——聊完后是否自动生成一张"精炼卡"并链回原文卡，还是只在原文卡上追加 notes？（倾向：追加 notes + 可选精炼卡，原话永远在。）
- O2：簇的历史版本保留策略（每次汇总都存快照？只存最新？）
- O3：散卡超过 N 条是否提示人"该汇总了"？（注意原则 5：不自动触发——只允许被动提示，且可关。）
