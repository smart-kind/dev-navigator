# Part A · 产品主干（原 prd.md，§1–§15）

## 1. 一句话产品描述

**Navigator 是一个 Spark 驱动的产品迭代系统**：把产品迭代中产生的一切模糊想法——使用反馈、验收意见、新点子、用户故事——忠实收进 **Spark 板**；攒到一定程度，由人发起、经**大脑**把 Spark 汇总分类、提炼成一张**完整的故事卡（= 目标）**，派发给空闲且有能力的 worker（agent）执行，产物经目标验收后合并回源码仓库。形成 **"Spark → 故事（目标）→ 执行 → 反馈（新 Spark）"** 的闭环。自托管在一台公网 VPS，浏览器即指挥台。

**流程模型的出处**：借鉴故事板驱动开发（storyboard agile）——板上每张**故事卡**是一件事，独立、端到端、有用户价值、可验收。本系统的不同在于多管了一层故事板没有的**前置层**：想不清楚的零星想法先落 Spark 板，想清楚、你拍板后才变成故事卡（目标）。

设计动机（用户亲述的三个痛点）：

| # | 痛点 | Navigator 的回应 |
|---|---|---|
| 1 | **目标跑飞 / 没完成标准** | 目标 = 故事卡，强制带"谁/要什么/为什么 + 验收标准 + 边界"；目标不可变只可取消 |
| 2 | **多机 / 多 agent 一片乱** | 能力注册 + 只派空闲 + 心跳活性 + 状态集中（Navigator 唯一事实源），worker 零暴露 |
| 3 | **状态全靠记忆和命令** | Web 统一可见：项目/目标(故事板)/任务/机器/Spark 板/架构 |

核心循环：

```
一切模糊想法（人 / AI / 验收 / 渠道）──► Spark 板（忠实记录，丢弃=状态不删除）
        ▲                                    │ 攒一堆后，人发起
        │                                    ▼
  新 Spark ◄── 验收反馈 ◄── 执行 ◄── 目标（=完整故事卡，独立 worktree）
                 │             大脑拆任务        │ 人拍板 → 大脑语义校验 → 引用 Spark
                 └──── 合并到主分支（目标验收通过后）  ▲
                                                    │
                                        Spark 汇总分类 → 提炼成故事卡
```

## 3. 名词解释（术语表）

> 术语表定义"词"。**专有名词 ≠ 系统实体**（哪些有身份/状态/生命周期见 §4）。详细设计口径以 Part C 为准。

| 词 | 定义 |
|---|---|
| **Navigator** | 中枢，跑在公网 VPS 上的常驻服务（唯一对外暴露点）。纯确定性骨架：状态机 + SQLite + WS server + 派发 + MCP server + HTTP API + Web UI。**零原生脑**，所有"想"外包给脑会话。 |
| **Worker** | 一台机器上的轻量常驻进程（不暴露端口，主动外连 Navigator）。配对/心跳/收派发/懒拉起 agent（ACP）/双向转发/如实上报状态。tmux 操作台。一台物理机可跑多个 worker。 |
| **Agent** | worker 本地干活的 AI CLI 实例：CC / Kimi / opencode（可能 pi）。各自配模型，按任务类型路由。 |
| **大脑（脑会话）** | Navigator 经 ACP 现请的"思考者"（现成 harness），用完回收不保留记忆。角色：**澄清员 / 规划师 / 汇总分类员 / 语义校验**。Navigator 有专用大脑承担自身认知工作。 |
| **Project（项目）** | 顶层空间，绑定**一个或多个源码仓库**。Spark、目标都在项目空间内。 |
| **Spark（零星想法卡）** | 系统唯一输入数据。一条使用反馈 / 验收意见 / 新想法 / 用户故事。**忠实记录原文，不成体系**；丢弃是状态不是删除。详细设计见 Part C1。 |
| **Spark 板** | 每项目一块，收集该项目所有 Spark 的"收/看/批/审计"界面（功能见 §6）。 |
| **簇（Cluster）** | 大脑对一批 Spark **汇总分类**的产物：一个主题 + 归纳 + 成员卡 + 代表卡。派生的，可重算。 |
| **丢弃 / 已考量** | Spark 状态。丢弃=不予考虑（胡扯/重复/不可行，不删）；已考量=被某目标引用覆盖（失效）。 |
| **故事卡（Story Card）** | **目标的书写形态**：作为【谁】，想要【什么】，以便【为什么】+ 验收标准 + 边界。想清楚的 Spark 经提炼变成故事卡；你拍板后故事卡=目标开工。 |
| **语义校验** | 定目标时大脑读架构记录，语义判断目标是否违背某节点职责/需新增节点——讨论依据，人拍板。 |
| **Channel / Conversation** | 渠道（Web 聊天、以后 Mattermost…）/ 一次与大脑的对话（渠道无关），Spark 最常见的落地现场。 |
| **Goal（目标）** | 项目内迭代单元，独立 worktree；开始后不可变只可取消。= 一张被采纳开工的故事卡。 |
| **Worktree** | git worktree，每个目标一个独立工位。 |
| **Task（任务）** | 目标的最小工作单元，大脑拆解（一个目标约 8 个任务）。 |
| **验收** | 任务级=agent 自验（内部修到过）；目标级=人对照故事卡验收标准判定，通过才合并主分支。 |
| **合并（Merge）** | 目标验收通过后并入仓库主分支（执行者待定，§14-①）。 |
| **拐弯** | **目标之间**的大方向选择（"本不想发明船，中期想发明船"）。目标内部永不拐弯；由人发起。 |
| **Evidence** | 干完的证据：commit 引用/改动摘要/日志/截图/报告。 |
| **ACP / MCP / WS 隧道** | ACP=驱动 agent 的协议（Navigator=client，agent=server，与网络拓扑无关）；MCP=Navigator 对外做 server、agent 外连查/写状态；WS 隧道=worker 外连 Navigator 的常驻通道，承载配对/凭证/心跳/ACP。 |
| **配对** | worker 连上未授权 → Navigator 侧输密钥批准 → 发设备凭证（可吊销）。 |
| **能力注册** | worker 启动自检后上报：引擎/模型、环境标签、常驻仓库。 |
| **ArchView** | 架构图=视图，描述任意范围，同项目可多张并存，不强制对应层级。实体/关系/职责/名词都是数据库记录。 |

## 4. 实体与关系（系统架构视图）

> 术语表管"词"，本节管"实体 + 关系 + 职责"。这些在系统里不是文档而是**数据库记录**（配合 ArchView 做语义校验）。

### 4.1 实体清单

| 实体 | 一句话定义 | 关键状态/属性 |
|---|---|---|
| **Person（账号）** | 能登录 Navigator 的人 | 用户名/密码 |
| **Channel（渠道）** | 输入/对话入口（Web 聊天页、以后 Mattermost…） | 类型 |
| **Conversation（对话）** | 一次与大脑的聊天，人和 Agent 都能参与 | 归属项目、参与方 |
| **BrainSession（大脑会话）** | 大脑的一次具体会话（澄清/规划/汇总分类/语义校验） | 角色、引擎、模型 |
| **Project（项目）** | 顶层空间 | 名称 |
| **Repo（仓库）** | 项目绑定的源码仓库（可多个） | git 地址、主分支 |
| **SparkBoard** | 每项目一块 | 归属项目 |
| **Spark** | 一条零星想法/反馈/故事（忠实记录原文） | 状态、星标、来源、派生簇、引用它的目标 |
| **Cluster（簇）** | 大脑汇总分类的产物 | 标题、归纳、成员卡、代表卡 |
| **Goal（目标）** | 项目内迭代单元 = 故事卡开工态 | 故事要素、验收标准、边界、引用 Sparks、worktree、状态 |
| **Task（任务）** | 目标拆出的最小工作单元 | requirement/验收词/engine/state |
| **Worker / Agent / Capability** | 执行进程 / AI CLI 实例 / 自检能力报告 | 凭证、心跳、状态；引擎、模型；能力清单 |
| **ACPSession（执行会话）** | 派发后临时建立、Navigator 驱动 agent 的会话 | 对应 Task/Agent，随任务回收 |
| **Evidence** | 干完的证据 | commit 引用、日志、截图 |
| **ArchView / ArchNode / ArchRelation / ArchTerm** | 架构视图 / 实体记录 / 关系记录 / 名词记录 | 用于语义校验与架构页 |

### 4.2 实体关系总图

```
 Person ──登录──► Navigator
   │
   ▼ 经某 Channel
 Conversation ──► BrainSession（澄清/规划/汇总分类/语义校验）
   │                        │
   ▼                        ▼
 Project 1──* Repo ── SparkBoard ──* Spark ──(大脑汇总)──* Cluster
   │                                    │                  │ 提炼
   │◄──── 被引用/已考量 ◄───────────────┤                  ▼
   ▼                                    │            故事卡 → Goal（人拍板）
 Goal（1──1 Worktree）───────────────────┘  1──* Task ──派发(能力+空闲)──► Worker ──* Agent
   │                                                              │ 在 Goal 的 Worktree 干活
   │◄──────────────── Evidence ◄───────────────────────────────────┘ commit/push
   ▼
 Goal 全部任务完成 → 目标级验收（人）→ 通过 → 合并主分支
   ▼
 验收不过 / 新想法 / 使用反馈 ──► 又一张 Spark（回到 SparkBoard，循环成立）
```

### 4.3 架构数据与语义校验

- 实体、关系、职责、名词全部是**数据库记录**；Navigator 自己的架构也按同一机制记录（dogfood）。
- **语义校验**：人发起定目标时，大脑读相关 ArchView，判断：动到哪些节点？是否违背职责？需不需要新增节点/改职责？——进提案给人讨论。非规则硬拦、非仅参考；决定权在人。
- Dashboard 设"架构"页：可视化 ArchView、节点职责、可编辑维护（M1+）。

## 5. 总体架构

### 5.1 部署形态

- Navigator 跑在**一台公网 VPS**，唯一对外暴露点；登录：简单用户名 + 密码。
- worker 全部**主动外连，零端口暴露**。
- **M0 单机调通**：Navigator 所在机器兼任本地 worker，走真实 WS 隧道（localhost）——本机与远程同一条代码路径。

### 5.2 角色与通道

| 通道 | 方向 | 用途 |
|---|---|---|
| WS 隧道 | worker(client) → Navigator(server) 外连 | 配对/凭证/心跳；推"开会话"；ACP 双向转发 |
| ACP | Navigator=client → agent=server | 驱动 agent 干活、驱动大脑思考 |
| MCP | agent(client) → Navigator(server) | agent 干活时查/写状态 |
| HTTP API | Web → Navigator | Web UI 数据 |
| git | worker 在 Goal 的 Worktree 上 commit/push | 代码产物；目标验收后合并主分支 |

### 5.3 连通层

1. Navigator 起 WS server；worker daemon 以 WS client 外连。
2. 配对：连上未授权 → worker 本地显示密钥 → Navigator 侧输密钥批准 → 发设备凭证（可吊销，重连自动认证）。
3. 心跳保活 + 断线重连（退避）；worker 如实上报状态迁移。
4. 派发 = 推"开会话" → daemon 懒启动本地 agent（ACP 模式）→ 双向转发 JSON-RPC；会话结束回收。
5. 敏感权限请求经 ACP 回用户授权。
6. worker 跑在 tmux：密钥显示、可 attach、可上手。

### 5.4 脑力来源

- **Navigator 零原生脑**；思考全外包：经 ACP 开会话请现成 harness（按角色/任务路由模型）。
- Navigator=记忆（SQLite），脑=现请的思考者（用完回收）——脑可换型号，状态审计不受影响。
- 专用大脑承担 Navigator 自身认知工作（澄清/汇总分类/拆解/语义校验/讨论方向）。
- 微判断人工兜底，以后可选轻量 LLM API。

### 5.5 状态存储

- **SQLite，Navigator 单写者**——worker 永不碰 DB；并发靠单写者消除。
- 状态机语义借鉴 loopx（goal/todo/gate/evidence），**独立实现**，运行期零依赖。
- 轻状态走 MCP/HTTP；重内容（代码产物）留在 git。

## 6. Spark 板（输入侧）

**摘要**（详细设计见 **Part C1**）：

- **铁律**：一切输入都是 Spark，不被直接执行。
- **忠实记录**：不管合不合理、有没有序，原样落卡；丢弃/已考量只是状态，永不删除。
- **落卡来源**：聊天即落 / 手动添加 / 验收不过自动落卡 / 讲一个故事 = 一张卡。
- **无强制标签**：建卡零摩擦，不带标签；检索靠语义搜索 + 大脑**汇总分类**（派生簇，可重算）；唯一手动动作是可选**星标**（你的意图，AI 替代不了）。
- **处理节奏**：没有人提醒；人主动攒一堆后发起"汇总分类"，抽出若干主题簇 → 提炼成故事卡（目标）。
- 生命周期四态：`new → 已归簇 → 已考量 / 丢弃`。

## 7. 目标与任务（目标 = 故事卡）

**摘要**（详细设计见 **Part C2**）：

- **目标的书写形态 = 一张完整故事卡**（借鉴故事卡/设计冲刺要素）：

```
作为【谁】，我想要【什么】，以便【为什么】
验收标准：怎么算完成（可验证，多条）
边界：明确不做什么（防跑飞）
引用：覆盖了哪些 Spark（标"已考量"失效）
```

- Project（多仓库）→ 多个目标（一个一个做）；目标在**独立 worktree** 工作。
- **目标不可变，只可取消**；想改 = 下一个目标。
- **无"方向错"**：目标是当时人+机器共同想法；错了就弃整个 worktree 重开。
- **拐弯 = 目标间大方向**，人发起：看 Spark 板 → 汇总分类 → 提炼故事卡 → 语义校验 → 拍板。
- **目标对齐（可选）**：目标执行前，人可随时发起"聊天对齐"——针对目标提问，大脑聚合**代码事实 / 你自己的用户故事 / 架构记录**作答；对话中超出目标的想法一键收为 Spark。**增量能力、无强制、不设规则闸门**（详见 Part C2 §4）。
- 大脑把目标拆成任务清单（约 8 个）；拆解时判可行性，不会拆出不可行任务。

## 8. 执行与验收（分层模型）

### 8.1 任务级（Agent 自验，不合并）

- Agent 执行任务；内部验证不过（如按钮点了没反应）→ **自己修复重做，直到自验通过**。
- 任务完成后**不合并**——成果留在分支（目标的"房间"里）；可上报 evidence。
- **无"任务失败"**：拆解时已判可行性，只有执行好坏。

### 8.2 目标级（人验收，通过才合并）

- 目标全部任务完成 → 人对照故事卡验收标准判定：
  - **通过** → 合并到主分支 → done；
  - **不通过** → 自动落一张验收 Spark（"败在哪"），与测出 bug 同构；无返工，补正 = 未来新目标。
- Evidence 任务级可见；合并只在目标验收通过后发生一次。

### 8.3 执行参数（可调，非设计）

会话时长上限、重试次数（默认 2）等均为配置；worker 掉线 = 会话中断，任务回队列可重派。

## 10. Navigator 职责清单

| 域 | 职责 |
|---|---|
| A. 收 Spark | 渠道接入（v1 Web 聊天）；一切输入=Spark 不直接执行；忠实记录；澄清 |
| B. 定航线 | 人发起；汇总分类成簇 → 提炼故事卡 → 语义校验 → 引用 Sparks 标失效 |
| C. 派发驾驶 | WS 推"开会话"→ 懒拉起 agent（ACP）→ 驱动/借脑力；权限回用户 |
| D. 状态中枢 | 状态机 + SQLite（单写者）；MCP server；HTTP API；Web UI |
| E. 管 worker | WS server + 配对/凭证/心跳；能力注册；按能力/空闲派发；目标验收后合并 |
| F. 记忆与脑 | Navigator=记忆；脑=现请思考者（专用大脑），用完回收 |
| G. 架构规格 | 维护实体/关系/职责/名词记录与 ArchView；语义校验（M1+） |

---

## 11. 里程碑

### M0 · 单机闭环（先做）

一台机器：Navigator + 一个本地 worker（真实 WS 隧道连 localhost），跑通完整执行闭环。
**可执行步骤见 Part C3**（拆到能照着做的粒度）。

M0 验收：手动跑通"建项目 → 定故事卡目标 → 拆任务 → 派发 → 执行自验 → 目标验收 → 合并主分支 → 看 evidence"一次；本机与远程同一条代码路径。

### M1+（草稿建议，待用户故事补齐后重排）

- Spark 板 v1：Web 聊天收卡 + 澄清 + 汇总分类 + 提炼故事卡
- 目标=故事卡全流程 + 目标对齐（可选聊天）
- 架构页与架构数据维护
- 多 worker / 远程机器接入
- Mattermost 渠道（= 另一个聊天）
- 合并执行模型定型、evidence 大件引用方案

---

## 12. 明确不做（首期范围外）

- 远程多机（M0 单机，代码路径与远程一致）
- 实时 ACP 驾驶 / 中途纠偏 / 中途改目标
- 重型人机介入机制（自主度分级、代理代决、任务中途停人复核）：不做——发起与拍板永远在人
- 定时调度 / 无人值守（用户未选为痛点）
- 部署环节（v1 不部署）
- Mattermost / 微信 / Telegram 接入（v1 只做 Web 聊天）
- "任务重做"概念（Agent 内部自修除外；补正=新目标）
- 目标中途变更（只可取消 / 弃 worktree）
- 架构"规则硬校验"（一律语义校验，人拍板）
- 建卡强制打标签（零摩擦；分类靠派生）
- 无人值守的任何自动触发（一切由人发起）
- 故事板式 sprint/时间盒/站立会仪式（故事板只取"故事+板+拉动"三层）

# Part B · 用户故事（原 user-story.md）

## 0. 出场人物与总览

- **我**：用 Navigator 迭代自己产品的人。一台常年开机的服务器（Navigator 住上面），几台装了 AI 助手的电脑（"机器"，随时待命）。
- **用户**：用我产品的人，觉得哪里不好用来提想法。
- **AI 助手（Agent）**：机器上干活的 AI。有擅长写代码的、写文档的、开浏览器做界面测试的。
- **大脑**：Navigator 请来"想事情"的 AI（澄清、分类、拆任务、把想法变成目标都靠它），用完就散，不留记忆。
- **Navigator**：中枢。自己不想，但记住所有状态、安排谁干活、把结果摆到我面前。

这套系统的日常循环，用一句话说：

> **谁有个模糊想法（包括我自己）→ 丢进 Spark 板（忠实记下来）→ 攒多了我发起一次"汇总分类"→ 挑出值得做的主题，让大脑写成一张"故事卡"（目标）→ 拍板开工 → 拆成小任务派给空闲的机器 → 干完我看结果 → 目标验收通过才合并 → 不满意的又变成新想法回 Spark 板。**

**一个重要的自我指认**：我们现在写这份文档、聊这些设计的过程，本身就是这个循环——对话里的想法是 Spark，这份用户故事是第一批故事卡，M0 实施步骤是拆出来的任务。

---

## 1. 打开 Navigator【现在】

出差回来，任何电脑开浏览器登录（用户名密码，略过）。

首页不用我回忆"上次干到哪了"，直接告诉我：进行中的目标（做到第几件任务）、机器们（谁在线谁在忙）、Spark 板又攒了多少新想法、最近动态流水。

**"现在是什么状况"是首页的第一责任。**

---

## 2. 建第一个项目【现在】

第一次用，引导我建项目：起名 + 绑定源码仓库。**一个项目可以绑多个仓库**（前端一个、后端一个都行）；项目下的想法、目标都在这个空间里，互不串味。

---

## 3. Spark 板：看想法【现在】

首页显示 Spark 板攒了 12 条新想法。点进去，每条是**原文优先**的一张卡，小字标着：谁提的、关于哪个项目、什么时候、什么状态（待处理 / 已归簇 / 已被某目标考量 / 已丢弃）。

我注意到两条标着"已丢弃"。点开看：一条是胡扯，一条跟另一条重复（它指着一行"内容重复，代表卡是 #47"）。**它们没被删，随时能翻出来**——丢弃只是"不予考虑"的状态。

我想找跟"设置"有关的想法，不用记得谁提过——直接搜"设置"，语义搜索把相关的都捞出来。**收进来的时候没人逼我打标签**，分类的事交给机器，我只管把想法倒进来。

---

## 4. 提想法：一条模糊的话怎么变成有用的【现在】

我自己也来丢一条。打开项目里的聊天框，随手写：

> "那个设置页感觉不太对，说不上来，就是…别扭。"

Navigator 没直接归档，而是请大脑先跟我聊两句：是找不到东西？看着乱？还是操作绕？……聊完，这条想法被澄清成"设置操作层级太深，期望常用项一步到达"，**原话也留着**。

以后用户从聊天软件发来的话，走的是同一个聊天框、同一道工序【以后】。

---

## 5. 定方向：几百条想法怎么变成下一个目标【下一步】

攒了小半年，Spark 板里有 80 条想法了。**没人提醒我**——是我自己觉得该想想下一步了。我点"汇总分类"，圈定这个项目：

大脑把这 80 条读一遍，吐出一组**主题簇**：

> **簇 A · 设置太难找** —— 7 条都在说这个（3 个用户 + 我验收时写的 2 条 + 2 条渠道反馈）
> **簇 B · 想要导出功能** —— 5 条
> **簇 C · 零零散散** —— 剩下 68 条没聚成气候，先不动

我从簇 A 里挑出代表卡，说："把它写成一张故事卡。" 大脑给我：

> **作为**用设置功能的用户，**我想要**常用设置一步到达，**以便**改个设置不用点三下。
> **验收标准**：最常用的 5 项设置首页可见一步可改；不再需要第三层页面。
> **边界**：不改数据格式、不动权限模型。
> 依据：簇 A 的 7 条想法（这些卡将被标"已被目标考量"失效）。

我看了一眼，验收标准改了一处，**拍板**。这就是一个目标——**一张想清楚的故事卡**。原来飘着的 Spark，在这一刻变成了板上要做的故事。

> 注意：方向不是灵机一动，是"攒想法 → 分类 → 提炼成故事卡 → 我拍板"。而且**不会为一个想法做一个目标**——一个想法只够当线索，凑成一群才成气候。

---

## 6. 目标开工：拆任务、派活【现在】

目标确立后，大脑把它拆成七八件小任务（拆的时候它就判断过可行性——不会拆出"摘月亮"这种干不了的任务），列给我过目，然后一件件派：

- Navigator 找**空闲**且有**能力**的机器，**直接派**，不商量；
- 机器上的 AI 在目标的**独立工位（worktree）**里干活——每个目标一个工位，互不干扰；
- Web 上能看到任务状态：排队 → 干起来了 → 完成。

**目标开工后就不会变。** 我中途想"顺便改改别处"？不行——那是下一个目标的事。想动，最多取消这个目标。这规矩治的是"目标跑飞"：目标不会在干活途中越长越歪。

---

## 7. 任务干完了：机器自己先验【现在】

一件任务干完，机器会**先自己验收**：它验证时发现"这个按钮点了没反应"，它会自己修、自己重跑，直到自己觉得过了，才上报"干完 + evidence（改了什么、提交记录、截图日志）"。

我在 Web 上能看到它干的活——**evidence 不是它说干完我就信，是我能看见**。

> 任务这一层，没有"失败"这个说法——只有干得好不好。干得不好，机器内部会自己修到过；真修不了的，它会停下来把原因说清楚，由我决定怎么办。

---

## 8. 目标做完：我验收，过了才合入【现在】

目标的所有任务都干完了。这时 **Navigator 还不会把代码合进主分支**——它先把整个目标摆到我面前：所有改动、evidence、对照当初那张故事卡的验收标准。

我看了，觉得"设置一步到达"做到了，但有两处命名我实在不喜欢。怎么办？

——**不返工**。我在验收框里写：

> "分组逻辑可以，但'高级'和'更多'两个名字太含糊。颜色对比度也低。"

这条话**自动变成一张新 Spark**，挂回这个项目的 Spark 板，来源标"验收"。目标本身我**不通过**——代码就不合主分支，这个目标先搁置。

> 这是整套系统最反直觉、也最关键的一条：**验收不过 ≠ 返工，验收不过 = 一条新想法**。我不陷入"让 AI 无限返工"的泥潭，把"哪里不行"的判断一次次沉淀下来。攒够了，下一张故事卡自然会带上"命名规范"这种教训。

（如果验收通过：目标合入主分支，正式完成。）

---

## 9. 拐弯：一个目标结束，下一站在哪【下一步】

无论"设置页"目标是完成还是搁置，只要我回到 Spark 板，看到那些攒下的验收意见、用户想法，我就知道：该让大脑再汇总分类一次、提炼下一张故事卡了——比如"重新梳理信息架构"（把命名的账一起算上）。

**拐弯不是中途改道**：是走完一个目标（或放弃一个目标），停下来，重新看 Spark 板，选下一个方向。如果发现某个目标整体就没做对（方向错了），我不会在错的基础上修修补补——**把这个目标的工位整个扔掉，重开一个新目标**。弃掉的是代码，留下的是"为什么错"这张 Spark。

---

## 10. 添一台新机器【以后】

家里添了台能开浏览器做界面测试的电脑，想让它也来干活：
- 那台电脑上跑一个轻量小程序，它**主动连上 Navigator**（不用开任何端口，躲在家庭网络后面也行），显示一串配对码；
- 我在 Web 上看到"有新机器请求接入，配对码 XXX"，核对批准；
- 机器上线前**自检**上报本事（有没有浏览器、装了哪个 AI、能碰哪些仓库），从此派活知道"界面测试找它"。

哪天不信任它，**吊销**凭证，它立刻变回陌生人。

---

## 11. 异常的一天【现在 + 以后】

- **Navigator 自己重启**：状态全在（存在它自己的库里），机器自动重连回来。
- **机器干到一半掉线**：任务不算"失败"，算"会话中断"——回队列，等它（或别的机器）重派；我看得见原因。
- **派错机器**（把写代码派给没装代码 AI 的机器）：理论上不发生（派发前按能力筛）；万一发生，机器会拒了并说明，任务回队列。
- **机器正忙**：任务排队，不硬塞。

---

## 12. 连起来看

```
第 1 章 打开首页 → 看清全局
第 2 章 建项目（绑一个或多个仓库）
第 3-4 章 Spark 板：收想法 / 聊天澄清 / 语义搜索（无强制标签）
第 5 章 攒多了 → 汇总分类成簇 → 提炼成故事卡（目标）→ 我拍板
第 6 章 拆任务 → 派空闲机器 → 独立工位干活（目标不可变）
第 7 章 机器自验 → evidence 可见（无"任务失败"，只有好坏）
第 8 章 目标级验收 → 过 = 合入主分支；不过 = 一条新 Spark（不返工）
第 9 章 目标结束 → 再看 Spark 板 → 下一个方向（拐弯在目标之间）
第 10 章 添机器（配对批准、能力自检）
第 11 章 兜底：重启不丢、掉线重排、忙则排队
```

一圈一圈，产品在"想法 → 故事 → 执行 → 反馈"里迭代——这就是 Navigator 存在的全部理由。而**我们现在写文档的过程就是第一圈**：想法（对话）= Spark，这份故事 = 故事卡，M0 步骤 = 任务。

# Part C1 · Spark 板 · 详细设计（原 specs/spark-board-design.md）

## 1. 设计原则

1. **零摩擦**：收想法比整理想法重要一百倍。建卡不带任何强制动作。
2. **忠实记录**：原文永不丢、永不删。丢弃/已考量只是状态。
3. **加工可重算**：标签、分类是**派生数据**，随时可由大脑重算，不是卡的固有属性。
4. **批量处理**：几百条 Spark 的处理是"批"不是"逐条"；单条只有收和状态流转。
5. **人发起**：没有任何自动触发；汇总分类、提炼故事卡都由人点。

---

## 2. Spark 是什么时候建立的（创建时机）

任何"一句还没想好的话"都可以立即成为一张 Spark：

| 来源 | 触发 | 落卡内容 |
|---|---|---|
| 聊天即落 | 在 Web 聊天（以后 Mattermost 等渠道）里说话 | 原话（含"我觉得不太对"这种模糊话） |
| 手动添加 | Spark 板页"添加一张卡" | 粘贴/输入的一段话、一条用户故事 |
| 验收自动落卡 | 目标级验收不通过 | 人写的验收意见（"败在哪"），来源=acceptance |
| Agent 落卡 | agent 执行中发现值得记的事（可选） | 其陈述 |
| 导入 | 把整段文字（如本文档）贴进来 | 一段文本，可拆多条或一条 |

规则：
- **创建即成功**：不校验"够不够清晰、有没有价值"——那正是后续加工的事。
- 每条卡保留**原文**字段；后续任何澄清/改写都**另存**，不改原文。

## 3. Spark 描述什么（内容结构）

```yaml
spark:
  id:                    # 稳定 id
  project_id:            # 属于哪个项目（必填——在哪块板）
  text:                  # 原文（核心，忠实，永不改）
  source:                # human | agent | acceptance | story | channel
  created_at:
  # —— 以下都是可空/派生/加工物 ——
  starred: false         # 用户手动星标（意图，AI 不代劳）
  status: new            # 见 §4
  discard_reason:        # status=discarded 时：胡扯 | 重复(→代表卡id) | 不可行
  considered_by:         # status=considered 时：被哪个 goal 引用
  cluster_ids: []        # 派生：进过哪些簇
  conversation_id:       # 澄清/产生它的聊天现场（可空）
  notes: []              # 加工记录：澄清改写、大脑标注等（只增不改）
```

**刻意不做**：不做结构化模板（谁/什么/为什么 那是故事卡的事）；不做建卡强制标签；不做优先级排序字段（那是簇/故事卡阶段的事）。

## 4. 生命周期（状态机）

```
                （人手动 / 聊天 / 验收自动）
                        │
                        ▼
                    ┌─ new（新收，待处理）─────────────┐
                    │                                  │
                    │ 人发起"汇总分类"                  │ 人点"丢弃"
                    ▼                                  ▼
              ┌─ clustered（已归簇）            discarded（丢弃）
              │   派生：cluster_ids 非空            · 胡扯 / 重复 / 不可行
              │                                  · 不删除，可回看
              ▼ 人拍板把它所在簇提炼成目标时         · 重复卡 → 指向代表卡
         considered（已考量 = 失效）
              · considered_by = goal_id
              · 不再参与后续汇总分类/提案
```

- 状态转换**只增不覆盖**：每次变化留痕（notes 或独立历史表），满足审计。
- `discarded` 和 `considered` 都是终态（卡不再流动）；唯一例外：人手动撤销（如"其实那条还能用"）→ 回到 new。

## 5. 标签策略（回应"建卡要不要打标签"）

**结论：建卡零标签；检索与分类全部派生。** 理由：

1. 分类可重算——AI 随时能对全量重分类，标签不必在创建时固化；
2. 创建时任何额外动作都在伤害"随手记"；
3. 语义搜索（自然语言）已能覆盖"找跟设置有关的"这类需求。

系统内两种"标记"分清楚：

| 标记 | 谁打 | 性质 |
|---|---|---|
| **星标 starred** | 用户手动 | 意图（"这条我特别在意"），AI 不代劳 |
| **簇 cluster_ids** | 大脑（汇总分类时） | 派生，可重算，不作卡固有属性 |

## 6. 汇总分类（批量加工，核心功能）

触发：人发起（圈定项目 / 时间段 / 全部）。

流程：
1. 人选择范围 + 提示语（可选："按痛点分"或"自由分"）；
2. 大脑读范围内所有 `new` + `clustered` 卡（`considered/discarded` 默认排除，可显式包含）；
3. 产出若干**簇**：

```yaml
cluster:
  title: "设置太难找"
  summary: "7 条在说同一件事：设置层级太深"
  member_sparks: [id…]
  representative: id   # 重复合并：代表卡
  duplicates: {id: id} # 重复卡 → 指向代表卡（重复卡标 discarded(重复)）
  suggested_story:     # 可选：大脑顺手草拟的故事卡（见 §7 与 Part C2）
```

4. 结果落库为视图/候选；大脑可解释"为什么这么分、哪些卡没进任何簇（散卡）"。

规则：
- 簇是**派生视图**：重跑会重新生成（可保留历史版本供对比）；
- 同义多条（你/我/他都说同一件事）→ 取一代表卡，其余标 `discarded(重复→代表卡)`——**不删除**；
- 散卡（没聚成气候的）留在 new，不强行归类。

## 7. Spark → 故事卡（目标）的通道

一条 Spark 不产生目标；**一个簇（或簇的组合）才可能产生一张故事卡**：

1. 人从汇总分类结果里挑一个簇（或跨簇挑几张卡）；
2. 让大脑把它们**提炼成一张故事卡**（要素见 Part C2：谁/要什么/为什么/验收标准/边界）；
3. 人过目修改 → **拍板** → 故事卡变 Goal；
4. 该簇涉及的所有 `new/clustered` 卡 → `considered(considered_by=该goal)`，不再参与后续提案；
5. 草稿故事卡（suggested_story）只是提案，拍板前不改任何卡状态。

## 8. Spark 板：界面功能清单

**收**
- 添加卡（textarea，零表单）；聊天入口（说话即落卡）；验收自动落卡入口（无界面动作）。

**看**
- 卡片流：原文大字优先；小字元数据（来源/时间/状态/簇/被引用目标/星标）；
- 展开卡：澄清聊天记录（conversation）、加工 notes、丢弃原因、重复指向；
- 筛选：状态 / 来源 / 时间 / 是否星标；**语义搜索**（自然语言）；
- 视图切换：全部 / 只看簇 / 只看散卡。

**批**
- 发起汇总分类（选范围 → 看簇 → 调整）；标丢弃（单条/批量，选原因）；星标/取消星标。

**审计**
- 任何卡不删除；状态与去向（被哪个目标考量）全可见；历史留痕。

## 9. 数量级与性能（设计假设）

- 单项目几百到几千张卡是常态；SQLite 全文/语义搜索够用；
- 汇总分类是重活（大脑要读全量卡）→ 建议按簇缓存 + 增量重跑，v1 可先全量重跑（量小）。

## 10. 开放问题（进 Part A §14 待决策）

- O1：澄清对话产物——聊完后是否自动生成一张"精炼卡"并链回原文卡，还是只在原文卡上追加 notes？（倾向：追加 notes + 可选精炼卡，原话永远在。）
- O2：簇的历史版本保留策略（每次汇总都存快照？只存最新？）
- O3：散卡超过 N 条是否提示人"该汇总了"？（注意原则 5：不自动触发——只允许被动提示，且可关。）

# Part C2 · 目标 = 故事卡 · 详细设计（原 specs/goal-story-card-design.md）

## 1. 核心命题

**目标是 Navigator 里唯一的"要做什么"实体，它的书写形态是一张完整的故事卡。**

借鉴故事板敏捷与设计冲刺类实践的目标卡要素：**谁（主角）→ 要什么（诉求）→ 为什么（动机）→ 验收标准（怎么算完成）→ 边界（不做什么）**。缺了这些，目标只是"一个待办标题"——正是"目标跑飞"的温床。

## 2. 故事卡字段

```yaml
goal:                       # = 一张被采纳开工的故事卡
  id:
  project_id:               # 挂在哪个项目（空间）
  story:
    who:                    # 作为【谁】——受益者/主角
    want:                   # 我想要【什么】——诉求（可多条）
    why:                    # 以便【为什么】——动机/价值
  acceptance:               # 验收标准[]：可验证，多条（防跑飞护栏）
  boundaries:               # 边界[]：明确不做什么（防蔓延）
  source:
    sparks: []              # 引用：覆盖了哪些 Spark（提炼它的簇/卡）
    story_from:             # 人写 | 大脑起草 | 从簇提炼
  state: active             # active | done | cancelled
  worktree:                 # 独立 git worktree
  created_at / decided_by:  # 拍板人（=人）
```

**每个目标必须同时满足**：story 三要素齐全（可人话读通）、≥1 条可验证的验收标准、边界非空（哪怕写"无"）。

## 3. 目标生命周期

```
（人从 Spark 板发起 → 汇总分类 → 挑簇）
        │
        ▼ 大脑起草故事卡（草案，不改任何卡状态）
    人过目修改 → 语义校验（大脑读 ArchView）→ 人拍板
        │
        ▼
   active：大脑拆任务（约 8 个）→ 逐任务派发执行
        │
        ├─ 全部任务完成 → 目标级验收（人对照 acceptance）
        │     ├─ 通过 → 合并主分支 → done
        │     └─ 不通过 → 自动落验收 Spark → 目标可取消/搁置（终态见 §5）
        └─ 人中途取消 → cancelled（worktree 保留或弃，产物处理见 §5）
```

**铁律**：
- active 期间目标**不可变**（story/acceptance/boundaries 都锁死）；想改 = 取消 + 新目标。
- 无"目标方向错"的修正流程：错了就取消/弃 worktree，教训落成 Spark。
- 拐弯只发生在目标之间（一个目标结束 → 重新看 Spark 板 → 下一个）。

## 4. 目标对齐（可选能力）

**命名**：不叫 QA——QA（问答式核查）只是目标对齐的**一种手段**。本能力是"制作目标的整个工作流程中，一个叫**目标对齐 / 聊天对齐**的功能"。

**定位与铁律**：
- **增量功能**：有人自己就能把目标对齐得很好，根本不需要这套"笨方法"——**不做也不会被拦**，没有任何规则强制它。
- **时机由用户把握**：目标**执行之前**，任何时间都可以做，想做几次做几次。
- **不要用规则绑架使用者**：不加闸门、不分级、不提示、不打卡。

**它是什么**：人对目标发起"聊天对齐"——针对目标提问，大脑**聚合目标 + 事实资源**作答（可行吗？覆盖吗？符合吗？），把目标的"责权利范围"对齐清楚。

**三种事实资源视角**（对齐时可按需取用）：

| 视角 | 对照什么 | 查什么 |
|---|---|---|
| 架构视角 | ArchView 职责记录（=原语义校验） | 会不会越某节点职责 |
| 代码事实视角 | 项目仓库当前代码（已存留的事实） | 可行吗？要动的地方现状？是不是已实现大半？ |
| 用户故事视角 | 人自己梳理的用户故事清单 | 你关心的项是否都进了目标？漏了什么？ |

**溢出回收**：对齐聊天中冒出**超出目标**的想法——用户知道现在不是讨论它的时候 → 一键**收为 Spark**（记下、不打断当前目标）。这是天然的 Spark 工厂，也守护"目标不可变"。

**语义校验（架构视角）细节**：大脑在起草/评审故事卡时读取相关 **ArchView**（实体/关系/职责记录），显式回答：

1. 这个目标会**动到哪些节点**（实体/模块）？
2. 是否**违背**某个节点的已声明职责？还是职责内的事？
3. 需不需要**新增节点**或**修改职责**？（若是，故事卡 boundary 里要写明，或另起一张"架构演进"卡）

输出进提案给人讨论。**不是硬校验**：不自动拒绝；语义判断可能错，所以人拍板。职责记录是散文，规则引擎拦不了——这正是要大脑"理解"的原因。

## 5. 终态与产物（含开放问题 N3 的默认）

| 终态 | 触发 | 产物处理 |
|---|---|---|
| done | 目标级验收通过 | 已合主分支；worktree 归档 |
| cancelled | 人中途取消 | 已完成任务的产物：留在分支（不并入主分支），worktree 保留一段观察期或弃；半成品不丢，可被未来目标捡起 |
| 验收不过 | 目标级验收不通过 | 默认：目标**不 done 也不自动 cancelled**，停在 active 但"阻塞验收"？——**N3 待决**。倾向默认：落验收 Spark + 目标置 `cancelled(带验收 Spark 引用)`，因为"补正=新目标"；人若想原目标续作，可"取消后立即以新目标重建（继承 worktree）" |

## 6. 轻量通道（开放问题 N2 的默认）

小到"改个错别字"也走完整故事卡 + 拆 8 任务太重。默认建议：
- **不设轻量通道，故意一律走重流程**——因为"顺手小改"正是蔓延的入口；
- 但允许"继承式小目标"：新目标可从旧 worktree 续作，拆 1 个任务就开工；
- 是否值得单独轻量通道 → Part A §14 待决策（N2）。

## 7. 与相邻实体的边界（防职责混乱）

| 实体 | 管什么 | 不管什么 |
|---|---|---|
| Spark / 簇 | 想法、线索、动机素材 | 不写验收标准、不拆任务 |
| **Goal（故事卡）** | 做什么 + 为什么 + 验收 + 边界 | 不写实现方案（那是任务级的事） |
| Task | 怎么干成（requirement/自验标准） | 不承载"为什么"（回溯到 Goal） |
| ArchNode | 某实体职责的长期声明 | 不承载一次性决策（那在 Goal 里） |
| Merge | 目标验收后的合入动作 | 不决定目标对不对（那是验收） |

- Spark 怎么变成故事卡：Part C1 §7
- 目标执行/验收/合并：Part A §8（分层模型）

# Part C3 · M0 实施步骤（原 specs/m0-implementation-steps.md）

## 0. M0 目标与验收

**目标**：一台机器上跑 Navigator + 一个本地 worker（真实 WS 隧道连 localhost），跑通：

```
建项目(绑仓库) → 定故事卡目标 → 拆任务(手动兜底) → 派发 → agent 在 worktree 执行自验
→ commit/push → 目标级验收 → 通过则合并主分支 → Web 看 evidence
```

**验收**：手动跑通上述链路一次；本机跑的与将来远程**同一条代码路径**（worker 不因"在 localhost"走任何捷径）。

**M0 不含**（M1+）：Spark 板/汇总分类/澄清、大脑规划（目标拆解先手动）、语义校验、架构页、远程机器、Mattermost。

---

## 1. 技术选型（已拍板）

**形态**：两容器分离——`navigator-core`（独立常驻 Node 服务，一切权威所在：HTTP API / WS hub / MCP server / agent 拉起 / 后台任务 / SQLite）+ `navigator-web`（Next.js：登录/用户体系/控制面板，调 core API + 连 WS）。全栈 Node/JS，**不引 Python**。

| 项 | 决定 | 备注 |
|---|---|---|
| 语言/运行时 | **Node.js + TypeScript** | 全栈同一语言 |
| 服务形态 | **两容器**：core 独立服务；web = Next.js | core 的活（WS/MCP/拉起/后台/权限权威）**绝不搬进 Next**，Next 只是 core 的客户端 |
| 仓库结构 | monorepo：`core/` `web/`(Next.js) `worker/`(daemon) `shared/`(类型与协议) | worker 与 core 同机可先跑，结构上独立 |
| 状态库 | SQLite（better-sqlite3），Navigator 单写者 | 经 Drizzle 抽象，可切 Postgres |
| DB 抽象层 | **Drizzle**（TS 定义 schema，驱动可换） | 切换 = 换 driver + 重跑 migration |
| HTTP/WS | core：Fastify（HTTP）+ `ws`（WebSocket server/client） | — |
| Web 框架 | **Next.js** | 团队访问/用户体系/项目权限的前端容器（选它：使用者最熟 + 权限/中间件组织友好） |
| 登录 | 用户名/密码 + bcrypt + 会话 | 权威在 core；web 侧会话 cookie / BFF 代理方式待细化 |
| ACP 驱动 | 子进程 stdio → JSON-RPC 桥接（见 S1 spike） | — |
| 合并 | v1 core 本体确定性合并（`git merge`），假设无冲突 | 冲突留给 M1 大脑 |
| Electron | 以后的可选壳（包同一套 web 产物），不影响本架构 | M0 不做 |

## 2. 步骤（每步都有验证）

### S1 · Spike：agent CLI 的 ACP 支持（最先做，风险最高）

- 目标：确认本机要驱动的 agent（CC / Kimi / opencode）哪个支持 **ACP server 模式**，怎么启动、走 stdio 还是 TCP、握手格式。
- 动作：各装/查版本；`--help` 找 acp 相关 flag；最小起一个会话，发 `session/new` + `session/prompt` 看回包。
- **验证**：记录下"哪个 CLI + 启动命令 + 消息样例"，写进 `docs/design/v0.1.2/specs/connectivity-notes.md`（实测记录，非空想）。
- 若某个 CLI 不支持 ACP：准备降级路径（见 S6 风险）。

### S2 · 脚手架 + 数据模型

- monorepo 初始化（TS、lint；包：`core/` `web/` `worker/` `shared/`）。
- SQLite schema（字段以 Part A §13 为准，M0 只建用得到的表）：

```
projects(id,name) · repos(id,project_id,path,branch) · goals(id,project_id,story_json,state,worktree_path)
tasks(id,goal_id,title,requirement,state,worker_id) · workers(id,name,state,last_heartbeat,token_hash)
sessions(id,task_id,worker_id,state) · evidence(id,task_id,commit_ref,summary,created_at)
sparks(id,project_id,text,source,status,created_at)   -- 仅验收落卡用，板功能 M1
```

- **验证**：migration 可跑、建删项目/目标/任务 CRUD 通过（脚本测试）。

### S3 · HTTP API 最小集 + 登录

- `POST /api/login`（用户名/密码 → token）；中间件保护其余路由。
- 项目/目标/任务的基础 CRUD + 列表（先不做完整 UI，接口先行）。
- **验证**：curl 走通 登录→建项目→建目标→建任务；未登录 401。

### S4 · WS 连通层（配对 + 心跳）

- `core/`：WS server，连接登记为"未授权 worker"。
- `worker/`：daemon 以 WS client 外连 `ws://localhost:PORT`；启动生成**配对密钥**并显示在终端（tmux）。
- Navigator 侧批准：`POST /api/workers/:id/approve {pairing_key}` → 发**设备凭证**（随机 token，存 hash）；worker 之后重连带凭证自动认证。
- 心跳：worker 每 N 秒发 ping；Navigator 记录 `last_heartbeat`，超时标 offline。
- **验证**：起 server → 起 daemon → 看"未授权"→ 批准 → 变 online；杀 daemon → 心跳超时变 offline；凭证吊销后重连被拒。

### S5 · worker 收"开会话"并拉起 agent（ACP 桥接）

- `worker/` 收到 Navigator 的 `session/open {task_id, worktree, engine}` 消息：
  1. 确认 worktree 存在（没有则按 S7 建）；
  2. 在 worktree 目录**懒启动** agent 子进程（S1 确认的 ACP 模式）；
  3. 桥接：Navigator 发来的 JSON-RPC → 写子进程 stdin；子进程 stdout → 回 WS。
- 会话结束（agent 退出/超时）→ 上报关闭，回收。
- **验证**：Navigator 能经 WS 给本机 agent 发一句 prompt 并拿到回复（等价于"借到了本地脑力"）。

### S6 · 派发（能力 + 空闲即派，无婉拒）

- worker 启动上报能力（v1 简化：静态配置"能跑哪些 engine"）。
- `POST /api/goals/:id/tasks/:id/dispatch`：找 online+idle+有能力 的 worker → 推"开会话"→ 任务 `queued→running`（worker 回报开始）→ 完成回报 `done` + evidence。
- 任务状态迁移只由 worker 上报触发；心跳丢失 → 任务 `interrupted`，可重派。
- **风险/降级**：S1 若发现某 CLI 不支持 ACP——降级路径：daemon 用该 CLI 的非 ACP 模式（如纯 `-p prompt` 一次性执行）包一层，能跑通 M0 即可，ACP 会话留到 M1；在 connectivity-notes 记录。

### S7 · git worktree + commit/push + evidence

- `POST /api/projects/:id/repos` 绑定时，本地准备：v1 用**本地 bare 仓库**当"主分支"（`repo_path/bare.git` + 一个 worktree 目录），避免污染真实仓库，且天然可测 merge。
- 目标开工：`git worktree add <goal-worktree> -b goal/<id>`（从 bare 的 main 检出）。
- agent 干完：在 goal-worktree 里 commit + push 到 bare 的 `goal/<id>` 分支。
- 上报 evidence：`{commit_ref, summary}`（diff stat / 变更文件清单）。
- **验证**：agent 的改动出现在 bare 仓库的 goal 分支；evidence 记录可查。

### S8 · 目标级验收 + 合并

- Web/API：列出目标所有任务 + evidence → 人验收 `POST /api/goals/:id/accept {pass: true|false, note}`。
- **通过**：Navigator 本体在 bare 仓库执行 `git merge goal/<id> → main` → goal `done`。
- **不通过**：自动落一张 Spark（`source=acceptance, text=note`）→ goal 置 `cancelled`（N3 默认，见 Part C2 §5）。
- **验证**：通过→main 有新提交；不通过→Spark 有记录、main 无该分支改动。

### S9 · Web 端（Next.js，独立容器/独立调试）

- `web/` Next.js 脚手架；本地 dev server + 代理到 core API（CORS/dev proxy）。
- 登录页（调 core 登录 → 会话）；项目列表；目标页（故事卡三要素 + 验收标准 + 边界 + 任务清单 + 每任务 evidence）；验收按钮。
- 样式不追求——**可见性第一**（参考 loopx dashboard 的信息组织，不做它的 UI）。
- **验证**：浏览器全程走完 M0 链路；core 与 web 各自独立起、独立停（验证隔离成立）。
